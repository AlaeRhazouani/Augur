What it does

Augur monitors the top 10,000 PyPI and npm packages — GitHub contributor activity, release patterns, dependency graphs, OpenSSF Scorecard checks and advisory history — and ranks them by the risk of a vulnerability advisory landing in the next 90 days. A second, separate module watches new releases for maintainer-takeover patterns. A tool-using assistant answers questions about a dependency tree with every claim tied to a retrieved OSV advisory ID. The whole system re-scores itself weekly against newly published advisories, and the CI pipeline blocks changes that make it worse.

The falsifiable thesis

Do public repository-health signals rank packages by near-term vulnerability risk better than popularity alone? Every model is measured against a popularity-only baseline, and the lift over that baseline is the headline number. Three outcomes are all presentable: clear lift means a working predictor; small lift means a feature-level explanation of what carries signal; no lift is a rigorous negative result, which is a stronger interview story than an inflated positive one. The engineering thesis stands alongside it: an AI system is production-ready only when it is observable, continuously evaluated and gated in CI.

Real problem it solves

Reactive security tools tell you too late

Snyk, Dependabot and Renovate all work the same way: an advisory is published, then they alert you. Augur reframes the question as triage — given finite review time, which dependencies deserve attention first, before anything is disclosed? That is a ranking problem, and ranking problems can be measured honestly.

The market is paying for exactly this

Socket.dev raised $20M for pre-publication supply chain analysis; Snyk is valued in the billions; commercial tools charge per developer per month. None of them publish their baselines or their error rates. Augur is the open, self-hosted version that shows its evaluation in full — including where it fails.

The two traps this design exists to avoid

Confounding. Popular, actively maintained packages get more advisories because more people audit them. A naive model learns "busy and popular = risky", which is the opposite of the intended story — hence the mandatory popularity baseline at every rung. Leakage. Fix commits and security releases usually land before the advisory is published, so a model anchored on publication date quietly learns to detect the fix already in progress. Augur anchors labels on the earliest disclosure signal and drops a 7-day blackout window before it. Both are tested, not assumed.

Why it stands out technically

Baselines are built before the model. B0 ranks by downloads, B1 by prior advisory count, B2 is logistic regression on both. Nothing is claimed as a result until it clears them by more than a bootstrap confidence interval. Most portfolio projects have no baseline at all.

Leakage is controlled and demonstrated. Strict time-based splits, features computed only from data dated before the snapshot, a unit test that fails if a feature query reaches past it, and a deliberate ablation showing what the metrics look like when the controls are removed. Very few candidates can discuss leakage from their own work.

The evaluation loop is the product. Weekly backtests on newly closed label windows, registry promotion gated on significant improvement, RAGAS in CI failing the build on faithfulness regression, and Prometheus alerts on precision decay. This is the MLOps job description, demonstrated rather than listed.

Deployable as a GitHub Action. A standalone action that scans requirements.txt or package.json and returns a ranked risk report is an artifact engineers can actually install — and it makes the repo self-demonstrating.

Free data sources — bulk for history, APIs for the daily refresh

OSV.dev bulk export

Ecosystem-native advisories for PyPI and npm with published dates and fixed versions. The label source — cleaner than mapping NVD's CPE strings back to packages.

GH Archive via BigQuery

Historical commits, contributors, issues and releases per repo, queryable by date partition. This replaces months of GitHub API crawling; 1 TB of queries per month is free.

deps.dev + OpenSSF Scorecard

Package-to-repo mapping, dependency graphs and weekly security-practice scores — branch protection, code review, fuzzing, pinned dependencies. Both free via BigQuery.

PyPI + npm registries

Download trends, release history, per-version publisher identity (npm), maintainer changes. Free, no auth for read access. Used for popularity features and the daily refresh.

Five components, each named for what it is

Only one of these is an agent. Calling an ETL job an "IngestionAgent" reads as agent-washing to senior engineers; naming things honestly reads as more mature, not less ambitious. The custom Python orchestrator stays — shared state, intent routing, retries with backoff, and a fallback chain to plain retrieval — because that is where the real coordination work is.

Component 01 · Ingestion pipeline

Backfill and daily refresh

Historical backfill from BigQuery: GH Archive activity, Scorecard checks, download history, joined to the 10,000-package universe via deps.dev. Daily refresh from the registries and the GitHub API. Every record validated against a Pydantic schema before it lands in TimescaleDB. Cron first, Airflow later if time allows.

Component 02 · Risk model service

Weekly ranking, Track A

One row per package per weekly snapshot, labeled positive if an advisory event falls 7–90 days ahead, with the 7-day blackout dropped entirely. LightGBM over seven feature families, benchmarked against B0/B1/B2, calibrated with isotonic regression, tracked in MLflow. Registry promotion requires beating production PR-AUC by more than the bootstrap interval — not just any F1 improvement.

Component 03 · Takeover detectors

Rule-based anomaly flags, Track B

Six transparent detectors: first-time publisher on a version, registry–repo mismatch, new install hook in a patch release, surprise young dependency, dormancy break by a new account, and maintainer handover. Each emits a flag with an explanation string. Thresholds tuned on three design incidents, then frozen before the held-out test.

Component 04 · Security assistant

The one real agent

Four tools — get_risk_score, get_takeover_flags, scan_manifest, search_advisories — over retrieval scoped to advisories for the 10,000-package universe rather than all 200K+ CVEs. Smaller corpus, faster evaluation, same skill signal. A post-check rejects any answer citing an OSV ID that was not actually retrieved. Open-weights LLM via Groq or Ollama, chosen in week 9 from what the free tier offers then.

Component 05 · Evaluation service

The differentiator

Weekly backtest of the risk model on newly closed label windows, RAGAS scoring on a 60-query golden set, CI gates in GitHub Actions that fail on faithfulness regression, and Prometheus metrics for both LLM quality and precision decay. This is the component that turns a demo into an LLMOps system, and it is never cut.

Dropped from v1, and why

TFT / darts. This is binary classification on windowed tabular features with few positives, not multi-horizon sequence forecasting. LightGBM trains in minutes and will most likely win. "Why TFT?" is a question that would not have had a good answer. It stays as a stretch goal only if it beats LightGBM on the same split.

Prophet baseline. A univariate time-series forecaster is not a baseline for a classification task. Replaced by B0–B2.

NVD as the label source. Mapping CPE strings back to PyPI and npm packages is messy and lossy. OSV is ecosystem-native and ships a bulk export per ecosystem.

Live GitHub API for history. Reconstructing metrics at T-90 for thousands of packages would hit rate limits for months. BigQuery does it in queries.

Baselines B0–B2, then the first LightGBM, all logged to MLflow. FastAPI shell and Docker Compose stack. Checkpoint 1.
Checkpoint 1 — week 4. If repo-mapping coverage is below roughly 60% of the universe, shrink to one ecosystem; npm has the better per-version publisher data. If LightGBM does not beat B2 at all, keep going — the thesis becomes the negative result, and weeks 5–7 become the explanation of why.

Week 5
Feature-family ablations, SHAP attribution, isotonic calibration, and hand-read error analysis on 20 false positives and 20 false negatives. Findings written into the repo, not just plotted.

Build the six takeover detectors against the design set — event-stream (2018), ua-parser-js (2021), ctx (2022). Rebuild each timeline from primary sources and verify every date before it goes in the README.

Evaluation service: weekly backtest job on newly closed windows, registry promotion gate, custom Prometheus metrics, Grafana dashboard. Checkpoint 2.
Checkpoint 2 — week 8. If you are more than one week behind, apply cuts 1 and 2 before starting the assistant. The evaluation loop ships before the chatbot, always — it is the part that differentiates the project.

Interview positioning — lead in this order

1

The baseline. "My first question was whether health signals beat popularity at all." This signals scientific thinking in one sentence, before any architecture is described.

2

The leakage story. The blackout window, the time splits, and the ablation showing what the metrics look like without them. Few candidates can discuss leakage from their own project.

3

The evaluation loop. Weekly backtests, the registry gate, the CI gate — how you know it still works next month, not just on demo day.

4

Then the architecture. If XZ Utils comes up, say it inspired the maintainer-trust features but is out of scope for a PyPI/npm system — it is a C library — and pivot to the event-stream result.
